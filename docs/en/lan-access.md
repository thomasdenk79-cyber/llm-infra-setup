# LAN HTTPS access for the Windows workstation (English)

A managed Caddy container (`llm-proxy`, Quadlet `quadlet/llm-proxy.container`)
serves HTTPS on port 443 to the LAN so the Windows PC can reach the portal,
dashboards and model APIs by name. Everything is generated by
`scripts/74-setup-local-proxy.sh` from `config/proxy/Caddyfile.template`;
decisions live in `config/host.env`, hand edits in generated files are not
allowed. Measured state: `docs/status.md` (section "LAN-Zugang ueber HTTPS",
2026-11-17). German walkthrough: `docs/operations.md`.

Contents: addresses · protection model · Windows 11 client · teardown ·
command list.

## Addresses

Published only on `127.0.0.1` and the addresses listed in `LAN_BIND_IPS`
(`config/host.env`). `LAN_DOMAIN` defaults to the hostname (`cachyos-x8664`).

| URL | Target | Measured |
|---|---|---|
| `https://homepage.<LAN_DOMAIN>/` | portal | 200 (also `/anleitung/`) |
| `https://grafana.<LAN_DOMAIN>/grafana/` | Grafana | 200, anonymous **read** role |
| `https://littlem.<LAN_DOMAIN>/v1` | LiteLLM gateway | 401 without a gateway key |
| `https://llm-direct.<LAN_DOMAIN>/v1` | alias of `littlem` | 401 without a key |
| `https://dozzle.<LAN_DOMAIN>/` | container logs | 200, no login; trusted LAN only |
| `https://direct-llm.<LAN_DOMAIN>/v1/models` | vLLM via the metrics forwarder | 200 without an API key or proxy login |
| any other name | fallback site | 403 or TLS abort, never proxied |

## Protection model

- LiteLLM (`littlem`, `llm-direct`) guards itself with its Virtual-Keys -
  a second password in front would be double work and would bypass key accounting.
- Dozzle has no upstream login and is intentionally served without proxy
  authentication on the trusted private LAN. Its logs can contain secrets from
  other containers; do not extend `LAN_BIND_IPS` to an untrusted network.
- The direct vLLM route intentionally has no API key or proxy login. Its trust
  boundary is the private network addressed by `LAN_BIND_IPS`; the host forwarder
  on port 30001 is also unauthenticated (`docs/runtime.md`).
- Grafana is reachable without login **by design** (anonymous read role, local
  network only).
- The proxy publishes HTTPS 443 on `LAN_BIND_IPS`; the separate vLLM forwarder
  on port 30001 is also reachable on the trusted private LAN and has no
  authentication (`docs/runtime.md`). Other backend ports remain loopback-only.
- `HOMEPAGE_ALLOWED_HOSTS` in `config/host.env` must include
  `homepage.<LAN_DOMAIN>`, otherwise the portal answers 400.

## Windows 11 client

Name resolution: `scripts/75-setup-local-dns.sh` (or `make local-dns`) runs a
dnsmasq zone for `*.cachyos-x8664` on this host and answers on the LAN address
only - no forwarding, so it is not an open resolver. Publish
`192.168.0.198` as the DNS server in the router and no device needs hosts
entries. Without router access, use the hosts line below instead. mDNS under
`.local` is deliberately not used: it would change every certificate name and
the portal's allowed hosts. Windows also appends the router's search suffix to
multi-label names, so `homepage.cachyos-x8664.lan` leaves the zone and goes to
the router instead. Use `nslookup -debug` at the device to see what actually
arrives, then add that suffix to `LAN_DNS_SUFFIXES` in `config/host.env` (for
example `lan fritz.box`) and re-run `make local-dns`.

Windows additionally must trust Caddy's local root CA.

Easiest: copy `scripts/windows-lan-client-setup.ps1` from this repository and
run it in an elevated PowerShell (idempotent, checks for admin rights, verifies
every route against its expected code):

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
.\windows-lan-client-setup.ps1 -LanIp 192.168.0.198 -Domain cachyos-x8664 -CertPath C:\temp\caddy-local-authority-root.crt
```

By hand it is three steps:

```bash
./scripts/74-setup-local-proxy.sh --print-hosts   # the ready-made hosts line
./scripts/74-setup-local-proxy.sh --ca-export     # CA path, fingerprint, Windows commands
curl -fsS http://192.168.0.198:8081/caddy-local-authority-root.crt -o caddy-local-authority-root.crt
```

The certificate download needs no SSH: the proxy serves exactly that one path on
port 8081 (everything else is 404), and the file is only the public key - the
fingerprint comparison below is what proves it is the right one. `scp
~/.local/share/llm-infra/caddy/ca/caddy-local-authority-root.crt
<user>@<windows-pc>:C:/temp/` still works as a fallback.

One block instead of handwork: the generator prints the whole PowerShell block for
the notebook (hosts entries, route test, root import with fingerprint check, every
route against its expected code) - paste it into an elevated PowerShell.

```bash
./scripts/74-setup-local-proxy.sh --windows-setup
```

```powershell
Add-Content -Encoding ascii C:\Windows\System32\drivers\etc\hosts "192.168.0.198 homepage.cachyos-x8664 grafana.cachyos-x8664 littlem.cachyos-x8664 llm-direct.cachyos-x8664 dozzle.cachyos-x8664 direct-llm.cachyos-x8664"
ipconfig /flushdns
certutil -addstore -f ROOT C:\temp\caddy-local-authority-root.crt
certutil -delstore ROOT "Caddy Local Authority"   # way back
```

Compare the fingerprint printed by `--ca-export` with
`certutil -dump C:\temp\caddy-local-authority-root.crt` before importing. Then
verify from the PC (same checks as `--check`, without `--resolve`):

```powershell
foreach ($h in "homepage","grafana","dozzle") { curl.exe -s -o NUL -w "$h %{http_code}`n" "https://$h.cachyos-x8664/" }
curl.exe -s -o NUL -w "direct-llm models %{http_code}`n" https://direct-llm.cachyos-x8664/v1/models
```

`llm-direct` is the LiteLLM gateway and answers 401 `No api key passed in.`
without a key - that is an authentication answer, not a network failure. The key
is `LITELLM_MASTER_KEY` in `~/.config/llm-infra/gateway.env` (print it with
`make show-credentials` on the Linux host):

```powershell
curl.exe -s https://llm-direct.cachyos-x8664/v1/models -H "Authorization: Bearer <master-key>"
```

Expected: 200 with the model list. `dozzle` is also unauthenticated;
`direct-llm`
is intentionally unauthenticated on the trusted LAN, while `llm-direct` uses
the gateway key.

### One name works, another does not

The DNS cache is keyed per name, not per zone. A name that was queried before
the zone existed keeps a negative answer in the Windows cache and in the browser
host cache, so it stays unfindable even though dnsmasq answers it. Prove it with
the pair that bypasses the cache:

```powershell
Resolve-DnsName homepage.cachyos-x8664            # uses the cache - often fails here
Resolve-DnsName homepage.cachyos-x8664 -DnsOnly   # asks the zone directly - the IP
ipconfig /displaydns | Select-String homepage     # shows the stored entry
ipconfig /flushdns
```

Then clear the browser host cache (`edge://net-internals/#dns` or
`chrome://net-internals/#dns`) and retry in an InPrivate window. If `curl.exe`
reaches the name but the browser does not, also turn off Secure DNS
(`edge://settings/privacy`, `chrome://settings/security`): DNS-over-HTTPS asks
public resolvers, which cannot know a private zone.

Acceptance at the device is the one open point (tracked as open item 18 in
`docs/HANDOFF.md`); record it in `docs/status.md` once done.

## Teardown

```bash
# in config/host.env:  LAN_BIND_IPS=   (set it empty)
./scripts/74-setup-local-proxy.sh        # re-renders without any LAN site
./scripts/74-setup-local-proxy.sh --check
```

The machine is then reachable exactly as before the LAN rollout (loopback
only). Old Dozzle credential files are removed by the generator. The sysctl
limit may stay; neither publishes anything on its own. The public Azure tunnel
is independent of this.

## Command list

```bash
make local-proxy                        # roll out: render, caddy validate, start/reload
./scripts/74-setup-local-proxy.sh --plan             # show pending changes, change nothing
./scripts/74-setup-local-proxy.sh --check            # end-to-end checks incl. LAN routes
./scripts/74-setup-local-proxy.sh --status           # unit, listeners, networks, LAN, CA, sysctl
./scripts/74-setup-local-proxy.sh --ca-import        # put the Caddy CA into the system trust (sudo, this host)
./scripts/74-setup-local-proxy.sh --ca-export        # CA file, fingerprint and Windows commands
./scripts/74-setup-local-proxy.sh --print-hosts      # hosts-file line for Windows
./scripts/74-setup-local-proxy.sh --windows-setup    # whole PowerShell block for the client
make local-dns                                      # roll out the LAN DNS zone (sudo)
./scripts/75-setup-local-dns.sh --plan              # show zone and systemd drop-in
./scripts/75-setup-local-dns.sh --check             # six names answered, no open resolver
./scripts/75-setup-local-dns.sh --remove            # take zone and drop-in back
```

A port, network or environment change restarts the container; a pure Caddyfile
change reloads via `ExecReload` without a restart.
